## answer

My recommendation is **Kanban • GitHub** as the starting template.

Not because we're adopting conventional Scrum or running a traditional software team, but because our central management problem is coordinating work between one human owner and multiple AI agents while controlling what can execute, what is waiting for approval, and how much work is active at once.

## answer

I have a strong recommendation, and one important correction to my earlier proposal:

**Do not create GitHub Issues for feature implementation tasks.** Your distinction is now clear:

- **GitHub Discussions (GD):** Features, product direction, architecture, design decisions and initiatives that need to be implemented.
- **GitHub Issues:** Possible or confirmed bugs and defects.
- **GitHub Projects — Kanban:** The actual implementation work queue, including tasks derived from Discussions and bug-fixing work derived from Issues.
- **GitHub Pull Requests:** Proposed code changes and reviews.
- **Miniapp Studio:** The execution control plane, authorization enforcement and durable evidence.

This gives us a clean division between deciding what to build, organizing the work, and actually executing it.

## **1. The complete operating workflow**

01 · Architecture

**ChatGPT — Architectural working session**

We discuss the vision, explore alternatives, settle trade-offs and lock decisions. I produce an implementation-planning prompt when you ask.

02 · Initiative

**GitHub Discussion**

You publish the prompt in GD. It becomes the durable initiative record and preserves the reasoning behind the work.

03 · Planning

**Planning agent**

Investigates the repository, reads the relevant architecture and milestones, drafts the implementation plan, and proposes small, dependency-ordered task packages.

Read-only unless the planning directive explicitly authorizes its specified documentation changes.

04 · Owner decision

**You approve the implementation plan and breakdown**

The accepted plan becomes the execution specification. The agent proposes Project Task Cards. You authorize their creation.

05 · Work management

**GitHub Projects — Kanban**

Each card is one bounded work package, with dependencies, executor, execution environment, acceptance criteria and authorization status.

06 · Execution

**Coding agents**

Agents pull eligible tasks, work in their assigned Local or Sprite environment, update progress, record evidence and ask for owner decisions at defined gates.

07 · Verification

**Review and acceptance**

Independent review where appropriate, tests, CI, PR review and owner acceptance. A green board card alone does not prove completion.

08 · Milestone closure

**GitHub Discussion and canonical docs**

Record what was delivered, what evidence supports it, what changed, and what should happen next.

The important distinction is that **the implementation plan is the specification; the Kanban cards are its executable work packages.** We should not make every line of the implementation plan a separate task.

## **2. What exactly goes into the Kanban board?**

There is a useful GitHub capability here: **Project Draft Issues**.

These are not repository Issues. They exist only inside the Project, and GitHub allows them to have a title, body, assignees and custom Project fields. That makes them suitable for our feature implementation tasks without violating your Issues-for-bugs policy.&#x20;

## **3. Division of labor**

I would formalize five responsibilities.

| Participant            | Primary responsibility                                                                                         | Must not do                                                         |
| ---------------------- | -------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| You — Project Owner    | Priorities, plan approval, authorization, consequential decisions and final acceptance                         | Delegate your authority implicitly                                  |
| ChatGPT — Architect    | Product vision, architectural reasoning, planning prompts, consistency checks and challenging proposed designs | Claim implementation evidence it has not inspected                  |
| Planning agent         | Repository investigation, implementation plan, task decomposition and dependency analysis                      | Begin implementation or create GitHub records without authorization |
| Execution agent        | Execute an authorized Task Card, update progress and produce evidence                                          | Expand its scope or self-authorize                                  |
| Reviewer agent / human | Independently challenge implementation and verify acceptance criteria                                          | Silently modify the implementation it is reviewing                  |

Miniapp Studio eventually becomes the enforcement and coordination layer between these participants.

### **The planning agent's deliverable**

I would require every implementation plan to include two distinct outputs:

**A. The implementation specification**

The architecture, decisions, interfaces, migration strategy, risks and acceptance requirements.

**B. The proposed Project Task Cards**

A structured task breakdown ready for your approval. Each proposed card must have:

- A unique task identifier.
- A concise outcome-oriented title.
- Source GD and plan section.
- Scope and explicit exclusions.
- Dependencies.
- Execution location: Local Desktop or Fly Sprite.
- Application and database targets.
- Authorization class and required approval.
- Verification evidence and acceptance criteria.
- Recovery or rollback.

The agent must identify which tasks are independent and which cannot begin until earlier work is accepted.

It should decompose work by independently verifiable outcomes, not by arbitrary file counts or tiny coding steps.

## **4. The Kanban lifecycle**

I recommend these statuses:

| Status      | Meaning                                                    |
| ----------- | ---------------------------------------------------------- |
| Proposed    | Task breakdown prepared; awaiting owner review             |
| Backlog     | Accepted work, but not yet eligible to execute             |
| Ready       | Dependencies clear and authorization granted               |
| In Progress | Agent or human has claimed the task                        |
| Blocked     | Waiting for a decision, dependency or environment          |
| In Review   | Implementation complete; evidence and review pending       |
| Done        | Acceptance criteria verified and owner acceptance recorded |
| Deferred    | Deliberately postponed                                     |

Authorization should be a separate field, not a column that can be bypassed by dragging a card.

**Separate authorization state**

Not requested

Pending

Approved

Refused

Expired

Revoked

Miniapp Studio's durable authorization record is authoritative. The GitHub Project field is only a visible representation.

### **Definition of Ready**

A card cannot enter Ready until:

1. Its source initiative and accepted plan revision are identified.
2. Its scope and acceptance criteria are clear.
3. Dependencies are satisfied.
4. Execution location and targets are specified.
5. The owner has authorized the required scope.
6. The correct workspace is available and not owned by another writer.

### **Definition of Done**

A coding agent cannot declare a task Done merely because it has finished editing files.

It must submit:

- What changed and why.
- Relevant Git diff or PR.
- Tests and their actual results.
- CI and other applicable verification.
- Artifact and deployment evidence where relevant.
- Outstanding limitations.
- Confirmation that no action exceeded the approved scope.

The status moves to In Review first. Done follows accepted evidence and the applicable owner/reviewer gate.

## **5. The improvements I strongly recommend**

These would make this considerably more effective than simply copying Jira's columns.

### **A. Build an Owner Inbox**

Highest-value addition

Rather than agents repeatedly interrupting you in chat, provide a single view for everything requiring your attention:

- Implementation plans awaiting approval.
- Proposed task breakdowns.
- Authorization requests.
- Agent questions and blockers.
- Scope-change proposals.
- PRs awaiting review.
- Deployment and migration approvals.
- Milestone acceptance.

Every request should explain:

**What do you need me to decide? Why? What evidence do you have? What exactly will my approval authorize?**

You should be able to approve or refuse a specific action without reconstructing the entire conversation.

### **B. Use a pull-based agent queue**

Don't make agents independently choose random work from the backlog.

Agents should pull only cards that are:

- Ready.
- Explicitly authorized.
- Within their assigned capability.
- Free of unresolved dependencies.
- Compatible with the workspace's active-writer lock.

This gives us controlled concurrency. Read-only research and independent reviews can run concurrently; code writers cannot compete for the same application workspace.

### **C. Version-pin the implementation plan**

This is particularly important.

Suppose we approve a plan, create 12 task cards, and then discover a better architecture while executing task 4.

We should not let agents continue blindly using the original plan.

Each task references the accepted plan revision. A material plan change triggers an impact assessment:

- Which existing cards remain valid?
- Which need updating?
- Which approvals are no longer valid?
- Are new tasks required?

This prevents architectural drift and stale instructions.

### **D. Make tasks proof-carrying**

Every completed task should carry its own evidence packet.

A task should be considered complete because its required conditions have been verified—not because an agent wrote "done" in a comment.

This is how Miniapp Studio can eventually distinguish an agent that merely produced code from one that delivered a proven result.

### **E. Introduce milestone closure**

When an initiative is complete, the agent prepares a milestone report linked to the original GD:

- Original objective.
- Accepted implementation plan.
- Completed and deferred tasks.
- PRs and commits.
- Verification results.
- Architectural decisions that changed.
- Remaining risks.
- Recommended next initiative.

You approve the report, and the important outcome is reflected in the canonical documentation and Discussion.

This creates institutional memory as the project grows.

## **8. One final strategic decision: continuous flow, not Sprints**

I would not introduce Scrum iterations yet.

We're initially operating with one human owner and potentially several specialized agents. We don't have a reliable historical velocity or capacity model. Let work flow continuously, with WIP control and explicit dependencies.

Introduce iterations later only when there is enough execution history to make capacity planning meaningful.

## **The operating principle I propose we lock**

**Discussions define what and why. Implementation plans define how. Project Task Cards define the units of work. Kanban governs flow. The owner authorizes. Agents execute. Reviewers challenge. Miniapp Studio enforces and records. Evidence determines completion.**

This gives us a Jira-like lifecycle without unnecessarily importing Jira's bureaucracy or confusing feature planning with bug tracking.

My strongest recommendation is to make **Owner Inbox, Agent Pull Queue, and proof-carrying tasks** first-class concepts in the eventual Miniapp Studio architecture. Those are the features that turn an ordinary Kanban board into a genuinely useful human-agent engineering operating system.

And one thing should remain non-negotiable: every coding agent must read its originating GD, accepted plan revision and assigned Project Task Card before acting. It must never treat an old chat response as greater authority than the latest accepted project record.
