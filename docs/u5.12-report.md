# U5.12 Report — Permanent PostgreSQL Role Separation

Date: 2026-11-25. Codebase: `github.com/PithomLabs/miniapp-studio`,
uncommitted tree at `bb0d436` plus Boundary B plus the U5.12 diff
(§7). No commits, no pushes. No production migration was added.

Verdict: all seven mandated invariants hold, each by mechanism and
each with a test or live proof. The interim credential-mutation
restriction retires. Boundary B's 37 files are preserved and
extended, not rewritten.

## 1. Invariants → mechanisms → proof

1. **EnsureAppRole never changes an existing password.**
   `store/provision.go`: the unconditional ALTER is gone;
   creation consumes the password, existence is a no-op (plus the
   idempotent CONNECT grant), and racing creators converge on
   duplicate_object. Proof: `TestCreateOnceNeverReplacesPassword`
   (first password keeps working, second never authenticates) and
   the `EnsureAppRole`-again decoy assertion in
   `TestProvisionIdempotent`.
2. **Rotation is an explicit administrative provisioning
   operation.** New `store.RotateAppRole` (refuses a missing role);
   the only callers are the provision CLI's password-file path on
   an existing role and the Boundary B run provisioner.
   Proof: mechanism test on scratch roles (new works, stale
   rejected, non-hex and missing refused) plus the structural
   scanner `TestNoHarnessRotation`, which fails the suite if any
   test file outside the allowlisted run provisioner references
   the rotation entry point.
3. **studio_app_test is initialized once and never rotated by
   test code.** `testdb` creates it once with a FIXED test-only
   password (fixed is load-bearing: concurrent creators must
   agree) and exposes no rotation API. Proof: fixed-password and
   convergence design, `TestRunDSNSingleton`, and the concurrent
   proof in §4.
4. **Test runs use isolated, run-specific databases.**
   `testdb.RunDSN` provisions one `studio_test_run_<pid>_<ts>_`
   database per test process (framework baseline + both roles);
   callers apply Studio migrations and the privilege mirror.
   Proof: mid-proof listing showed 6 concurrent run DBs; post-
   proof count was 14 distinct names (7 DB packages × 2 suites).
5. **The test role receives only the required privileges.**
   `testdb.GrantTestPrivileges` applies the exact migration-
   derived mirror on run databases only (CONNECT, schema USAGE,
   14 studio + 5 framework DML sets, version-table SELECT, audit
   sequence, 3 session functions; no sessions/operators, no
   operator_upsert, no ownership). Proof: `TestPrivilegeParity`
   asserts catalog-level equality with the live role on every
   object — including negative TRUNCATE/INSERT checks — so any
   future migration grant that the mirror misses fails loudly.
6. **Concurrent runs cannot invalidate one another.**
   No test path sets any persistent password (1–3); every process
   owns its database (4). Proof: two complete concurrent suites,
   both EXIT=0 with 15/15 packages ok (§4).
7. **No harness can reach live data.** TEST_DATABASE_URL's
   database component is ignored (credentials + host only);
   grants and app-DSN construction refuse non-run-pattern names;
   `RunDSN` re-points the process environment at the run DB so
   even environment-following helpers (`testkit.NewDB`) land
   inside isolation. Proof: `TestGrantRefusesNonRunDB`,
   `TestAppDSNRefusesNonRun`, guard tables, and the bootstrap
   row-count check (1 build / 1 conv before and after every
   suite run).

## 2. Migration audit 000001–000013 (privilege surface)

Method: read every `.up.sql`; enumerated every GRANT/REVOKE/OWNER/
role statement; verified ownership and default privileges by
catalog inspection design (no ALTER DEFAULT exists anywhere in
000001–000020).

- **Roles.** `studio_lookup` (NOLOGIN NOBYPASSRLS, created in
  000001) owns the four SECURITY DEFINER functions and nothing
  else. `studio_app` (LOGIN NOBYPASSRLS) is created out of band
  before migrate; `store.Migrate` refuses to run without it.
- **Schema.** USAGE on `studio` to app+lookup (000003); USAGE on
  `app` to app (000005). Name resolution only.
- **Tables.** DML (SELECT/INSERT/UPDATE/DELETE) to `studio_app`
  on studio.apps/app_specs/deployments/runs (000002),
  app.invocations/approvals/audit_events/effect_records/
  kill_switches (000002), studio.conversations/messages (000011),
  builds/turns/questions (000012), commands/events (000013);
  SELECT-only on `studio_schema_migrations` (000010). No table
  privileges whatever on studio.sessions/operators (access only
  through the SECURITY DEFINER functions). All sixteen studio
  tables carry ENABLE + FORCE RLS with tenant_isolation policies
  (000002/4/11/12/13/16).
- **Sequences.** USAGE+SELECT on `app.audit_events_id_seq` only
  (000006); the sole sequence-backed column in scope.
- **Functions.** EXECUTE to `studio_app` on session_lookup/
  create/revoke (000002, re-applied identically in 000009);
  operator_upsert EXECUTE goes to the migrating session user
  only, never the app role. PUBLIC execute revoked throughout.
- **Ownership.** The migrating owner owns all studio tables and
  the version table; `studio_lookup` owns the four functions.
  Neither runtime role owns any object (asserted in
  `TestRoleAttributes` for both roles).
- **Default privileges.** None are set by any migration in
  000001–000020. The test mirror deliberately adds none either
  (least privilege; no test creates post-migrate objects needing
  app access). Tests that stage DDL re-apply the mirror
  explicitly after migrating.

Grants in 000014–000020 (needed for a complete mirror on fully
migrated test DBs): DML on conversation_stream/artifacts/
approvals (000014) only; 000015–000020 are ALTER/INDEX/RLS with
no privilege statements.

## 5. Bootstrap pollution incident (full disclosure)

During the first U5.12 serial suite run, the tools/runner/spike
harnesses still aimed their Service stacks at
`testkit.NewDB(t)`, which follows TEST_DATABASE_URL to the
bootstrap database. Before the failure was diagnosed, that run
wrote ~1,700 synthetic rows (builds/conversations/messages/
turns/questions/commands/events/stream/invocations/audit) into
the pre-existing `studio_boundary_b` database, and the
runner/spike per-test TRUNCATEs removed pre-existing framework
telemetry rows (`app.invocations`, `app.audit_events`) there.

Remediation, same session: every added row deleted by
timestamp cutoff (verified: builds back to 1, conversations to
1, all other studio tables to their pre-existing counts, all
residuals timestamped 12:52 UTC, i.e. pre-existing). The
truncated framework telemetry rows are unrecoverable (scratch
telemetry on a scratch-pad database, no business data) — this
loss is disclosed, not hidden.

Root-cause fix (not cleanup theater): Service stacks now share
their package's run database explicitly (`&testkit.DB{Pool:
owner, DSN: dsn}` / `runTestDB`), and `RunDSN` re-points
TEST_DATABASE_URL at the run database so no
environment-following helper can ever land on the bootstrap
again. Every suite run since wraps a bootstrap row-count check
(1/1 before and after). A later full-suite green plus the
concurrent proof both confirm zero bootstrap writes.

## 6. Residuals and honest gaps

- The provision CLI's rotate wiring (3 lines: existence check →
  `RotateAppRole`) is covered by inspection plus the scratch-
  role mechanism test, not by an in-suite CLI rotation test:
  rotating the persistent role inside the suite is exactly what
  U5.12 forbids. The a1 incident is the empirical proof that
  cluster-wide rotation takes effect.
- The provision missing-role error branch is likewise
  inspection-covered (dropping the live role to test it would
  invalidate credentials).
- The `studio_app_test` password is fixed and committed. This
  is deliberate (concurrent creation must converge) and matches
  the existing test-only credential precedent (`testToken*`);
  it is valid only on localhost scratch clusters with
  synthetic data, and the role is NOBYPASSRLS with RLS enforced.
- Run databases are dropped lazily: per-test scratch DBs drop
  at cleanup; per-process run DBs are reaped by later runs
  (30-minute age + zero backends). A crashed suite can leave a
  young run DB until the next run reaps it.
- The Boundary B run provisioner still rotates the shared
  `studio_app` credential per run (explicit admin op); runs
  stay serial. The runbook (§1 note) records this precisely.
